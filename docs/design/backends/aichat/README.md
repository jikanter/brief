# aichat / eridian-ai Backend

**Status:** Proposed. Not in the phase2-synthesis P4 roadmap; this is a new target. Audit conducted 2026-04-27 against `~/Developer/Projects/aichat` source and a production config dir at `~/Library/Application Support/aichat` (155 roles, 14 sessions, 18 prompts, 15 RAGs, several agents).

aichat (renamed `eridian-ai` in the user's fork) describes itself as a "make for AI tooling" — a CLI runtime that loads roles, agents, prompts, sessions, RAGs, and macros from a configuration directory. Its on-disk format is a natural emit target for `brief`: most artifacts are Markdown-with-YAML-frontmatter or pure YAML, and the format-first decision recorded in design-decisions.md applies cleanly.

## Scope decision: agents-first

Of the five aichat artifact types, only one is high-leverage for `brief`:

| Target | Value | Recommendation |
|---|---|---|
| **Agents** | High — multi-file directory layout, declarative tool/variable manifests, model overrides, dynamic instructions; this is exactly what `brief` already encodes | **Implement first.** Primary deliverable. |
| Roles | Low — users tend to author roles by hand; format is so simple (a `.md` file with optional frontmatter) that a `brief` emitter saves <60 seconds of typing | **Defer or skip.** Re-evaluate only if a clear use case emerges. |
| Prompts | Very low — even simpler than roles (raw `.md`, no schema). Same authoring economics. | **Skip.** |
| Sessions | Low — primarily generated by aichat at runtime; a starter file is feasible but adds little value | **Skip in v1.** |
| RAGs | Out of scope — files contain materialized embedding vectors produced by `Rag::init`. Not human-authorable. | **Never.** |

The rest of this doc treats agents as the canonical case.

## Target file structure (agents)

aichat agents are **directories**, not files. Two locations, by design:

| Path | Purpose | Authored by |
|---|---|---|
| `<functions_dir>/agents/<name>/index.yaml` | Definition: identity + system prompt + variables | Tool/agent author (often vendored in a separate repo) |
| `<functions_dir>/agents/<name>/functions.json` | OpenAI-shaped tool declarations | Generated by `argc build`, not hand-written |
| `<config_dir>/agents/<name>/config.yaml` | Per-user overrides: model, temperature, tool selection | End user |
| `<functions_dir>/agents/agents.txt` | Newline-separated registry; aichat reads this to discover agents | End user / tool |

**The discovery key is `<functions_dir>/agents/<name>/index.yaml` plus an entry in `agents.txt`.** Without both, the agent is invisible.

In the user's production setup, `<functions_dir>` is a symlink to a separate `llm-functions` repo where `index.yaml` files are vendored. `<config_dir>/agents/<name>/config.yaml` is per-machine override. **Brief should default to emitting only the user-side override** (`config.yaml`), with a flag to additionally emit the upstream `index.yaml` for users who do not separate the two.

[open-question] Should `brief emit aichat agent` default to emit-override-only or emit-both? Emit-both is more self-contained but conflicts with the user's actual workflow of vendoring `index.yaml` in a separate repo.

## Schemas in scope

### `index.yaml` (definition)

```yaml
name: <slug>                  # required (cosmetic; runtime uses dir name)
description: <one-line>       # default ""
version: "0.1.0"              # default ""
instructions: |               # default "" — system prompt
  ...multi-line markdown...
dynamic_instructions: false   # default false; true means runtime-templated
variables:                    # default []
  - name: <slug>
    description: <inquire prompt label>
    default: <optional string or {shell: "..."} >
conversation_starters:        # default []
  - "..."
documents:                    # default []; glob/path/url, fed to RAG init
  - "./docs/**/*.md"
```

Every field has `#[serde(default)]` — minimum viable file is one line (`name: foo`). aichat treats agent YAML strictly: any parse error fails loading with a wrapped serde error.

### `config.yaml` (override)

```yaml
model: <client>:<model>       # optional
temperature: <float>
top_p: <float>
use_tools: <comma,sep,names>  # alias "tools"
agent_prelude: <session_name> # optional warm-up session
instructions: <string>        # override; ignored when dynamic_instructions=true
variables:                    # IndexMap<String, String> (flat key:value)
  os_version: tahoe
output_schema: <JSON Schema>
input_schema: <JSON Schema>
pipe_to: <string>
save_to: <string>
```

All fields optional; missing values inherit from global `config.yaml`. Per-agent env-var overrides exist (`<NAME>_MODEL` etc.) but are runtime-only.

### `agents.txt` (registry)

Plain text, one slug per line, `#` comments allowed. Idempotent append.

## Mapping brief content to an aichat agent

| Brief field | aichat destination | Notes |
|---|---|---|
| H1 goal | `description:` (one-line) and lead paragraph of `instructions:` | Truncate goal for `description:` |
| `frontmatter.skill_name` (if present) | agent slug + `name:` | Falls back to a slug derived from the goal |
| `frontmatter.model` | `config.yaml: model:` | Format must be `client:model_name`; validated at use-time |
| `frontmatter.context` | `index.yaml: documents:` | aichat feeds these to per-agent RAG init |
| `frontmatter.stack` | freeform mention in `instructions:` preamble | No structured slot |
| `constraints.hard` | `instructions:` "## Rules / You MUST" block | Reuse the skill emitter's voice |
| `constraints.soft` | `instructions:` "Prefer..." block | |
| `constraints.ask_first` | `instructions:` "Ask before..." block | aichat agents support interactive prompts via `variables:` — natural fit |
| `sacred` | `instructions:` "Do not modify:" block | aichat has no native sacred concept — embed inline |
| `assumptions` | `conversation_starters:` (validated ones) or inline section | Lossy by design |
| `deliverable` | trailing paragraph of `instructions:` | |
| `unknown_sections` | preserved as additional instruction blocks | Same passthrough discipline as other emitters |

Tool declarations (`functions.json`) are out of scope: brief does not model tool schemas, and they are normally produced by `argc build` from comment-tagged scripts.

## Idiomatic register

The user's production roles and agents skew **terse and conversational** — most are <30 lines, often a single paragraph. Brief's NEVER/MUST/PREFER/STOP register would produce unidiomatically long agent instructions if applied verbatim.

The skill emitter's voice ("You MUST follow these rules:" / "Prefer these approaches:" / "Ask the user before proceeding with:") is a closer fit than the claude emitter's `**IMPORTANT:**` bullet style and should be the starting point.

[open-question] Should `aichat agent` emit support a `--terse` mode that compresses constraints into a single paragraph, mirroring the user's actual authoring pattern for short agents?

## Templating placeholders to preserve

aichat instructions support several placeholder shapes that emitted output must not mangle:

- `__INPUT__` — literal user-input marker (constant `INPUT_PLACEHOLDER`)
- `{{__tools__}}` — replaced at load time with the agent's tool list
- `{{__os__}}`, `{{__shell__}}`, `{{__now__}}`, `{{__cwd__}}`, `{{__model_id__}}`, etc. — built-in variables
- `{{<user_var>}}` — user-defined variables from the `variables:` block
- `{{$AICHAT_FOO}}` — env-var interpolation (only `AICHAT_*` allowed)
- `{{#if VAR}}…{{/if}}` / `{{#unless VAR}}…{{/unless}}` — conditional blocks

Any `brief` content already containing these tokens must round-trip unchanged. The emitter should not YAML-escape `{{` / `}}` and should not rewrite `__INPUT__`.

## Model identifier handling

aichat parses model IDs as `<client_name>[:<model_name>]`. Resolution order at use-time:

1. Exact match in the registered model catalog (`models.yaml` + `config.yaml` clients).
2. If client is recognized but model is not, **synthesize on the fly** for chat models — aichat is permissive here.
3. Bare `<client_name>` picks the first registered model for that client.
4. Unknown client → `bail!("Unknown {model_type} model '{id}'")`.

**Implication for brief:** `frontmatter.model` can be passed through unchanged when it already looks like `client:model`. When it does not (e.g. `claude-opus-4-7`), the emitter has two options: leave it as a bare model name (which aichat will treat as a client name and likely error), or prefix a default client. **Recommendation:** emit `model:` only when the source value contains a `:`; otherwise omit and let aichat fall back to the global `config.yaml` default. Document this in the user-facing output.

[open-question] Should brief learn an explicit `client:` frontmatter field, or stay with the convention that `model:` carries the full `client:model` string when targeting aichat?

## Why this is more than a "trivial wrapper"

Three concerns make `aichat agent` more involved than the copilot/windsurf-class emitters:

1. **Multi-file output.** brief has no infrastructure for emitting more than one file today. Every existing emitter returns `String` and prints to stdout; only `--install` writes a single hardcoded path. An aichat agent emit produces at minimum `<config>/agents/<name>/config.yaml`, optionally also `<functions_dir>/agents/<name>/index.yaml`, and an idempotent append to `<functions_dir>/agents/agents.txt`. This is the dominant scope item.

2. **Registry mutation.** `agents.txt` must be appended to for the agent to be discoverable. The user's production `agents.txt` is symlinked into a separate repo. Options: append idempotently (skip if line already present), warn-and-skip with the line printed for manual paste, or emit a `--dry-run` patch.

3. **Config-dir discovery.** aichat resolves its config dir from `$AICHAT_CONFIG_DIR`, `$XDG_CONFIG_HOME/aichat`, or `dirs::config_dir()/aichat` — but the eridian-ai fork uses `eridian-ai` as the directory name (the `CARGO_CRATE_NAME` is baked in at build time). brief needs a strategy: hardcode `eridian-ai`, honor `$AICHAT_CONFIG_DIR`, expose a `--flavor aichat|eridian-ai` flag, or take an explicit `--output <dir>`.

[open-question] Should brief default to `--output` required for aichat emit (forcing the user to point at the right config dir each time), or auto-detect via `$AICHAT_CONFIG_DIR` + a fork-aware default?

## Required scaffolding in brief itself

Before the aichat emitter can be written, the following infrastructure changes are needed. None are aichat-specific; they unblock other multi-file backends (e.g. cursor, aider full-integration) too.

1. **Multi-file emit return type.** Either widen emitter signatures to `enum EmitOutput { Single(String), Files(Vec<(PathBuf, String)>) }`, or add a sibling `install_aichat(&Brief, &Path) -> Result<()>` that mirrors the existing `install_claude` / `cmd_skill_emit` pattern. The sibling-function approach is less disruptive and matches existing precedent.
2. **`--output <dir>` CLI argument**, gated to targets that need it.
3. **Widen `--install`** past Claude-only at `src/main.rs:260`.
4. **Idempotent file-append helper** for `agents.txt` (skip if line already present).

The `Brief` model itself needs no changes — every field aichat plausibly consumes is already there.

## Sessions: deferred

A starter session file is technically feasible (two-line minimum: `model:` plus `messages: []`), but offers little value over running aichat once and saving the session. Sessions are primarily a runtime artifact. Revisit only if the user identifies a workflow where a tool-emitted session starter beats `aichat --save-session`.

## Roles and prompts: deferred

The user has confirmed that roles are authored by hand. Format simplicity (a `.md` file with optional frontmatter) means a brief emitter would save <60 seconds — below the threshold of project value. Defer indefinitely; revisit if a use case emerges (e.g. emitting a brief into both Claude Code and aichat in one operation).

## Action checklist for implementation

When picking this up:

1. Land the multi-file emit scaffolding first — it is the bulk of the work and benefits other planned backends.
2. Implement `brief emit aichat agent` producing `config.yaml` only, with `--with-definition` to additionally produce `index.yaml`.
3. Implement idempotent `agents.txt` append, with `--no-register` to skip.
4. Add fixture-based integration test that emits an agent into a `tempfile::tempdir()` and asserts on the directory tree.
5. Round-trip the existing `.brief.md` at the root of the production config dir as a real-world integration test.
6. Verify aichat's current schemas against the source tree before shipping — the upstream evolves quickly. Specifically re-check `AgentDefinition` (`src/config/agent.rs`) and `AgentConfig` field lists.
